Node & Pod 네트워크 통신: Native vs VXLAN

서로 다른 네트워크 대역에 노드가 위치할 때 autoDirectNodeRoutes의 한계와 Static Routing, 그리고 이를 해결하는 VXLAN Overlay 모드의 동작 원리를 비교합니다.

Native Routing Mode와 다른 대역 노드 통신 문제

k8s-ctr과 k8s-w1은 같은 /24 대역에 있고, k8s-w0는 다른 네트워크 대역에 배치된 환경에서 autoDirectNodeRoutes=true를 사용하면 같은 L2에 있는 k8s-w1의 PodCIDR만 커널 라우팅에 추가되고 k8s-w0 경로는 추가되지 않습니다.

  • Native 모드 장점: Overlay가 없어 MTU 손실이 없고 캡슐화/디캡슐화 부하가 없어 네트워크 지연이 최소화됩니다.
  • Native 모드 단점: 다른 네트워크 대역에 대해서는 BGP 에이전트나 네트워크 장비의 라우팅 설정이 필요합니다.
bash
# Static Routing 수동 추가 예시 (현실적으로 대규모 운영에서는 비권장)
# k8s-ctr
ip route 172.20.0.0/16 via 192.168.10.200 dev eth1 proto static

VXLAN Overlay Network Mode 구성 및 검증

PodCIDR 라우팅을 네트워크 장비에 일일이 넣기 어려운 환경에서는 VXLAN Tunnel 모드를 사용합니다. NAT가 Src IP를 변경·추적하는 것과 달리, VXLAN은 기존 패킷에 Node IP 헤더와 VXLAN 헤더를 캡슐화(Encapsulation)하고 목적지에서 디캡슐화합니다.

bash
# VXLAN 커널 모듈 확인 및 로드
grep -E 'CONFIG_VXLAN=y|CONFIG_VXLAN=m|CONFIG_GENEVE=y|CONFIG_GENEVE=m|CONFIG_FIB_RULES=y' /boot/config-$(uname -r)
modprobe vxlan
lsmod | grep -E 'vxlan|geneve'

# Cilium Tunnel(VXLAN) 모드로 업그레이드 (변경 시 약 5개 ping 순단 발생)
helm upgrade cilium cilium/cilium --namespace kube-system --version 1.18.0 --reuse-values \
  --set routingMode=tunnel --set tunnelProtocol=vxlan \
  --set autoDirectNodeRoutes=false --set installNoConntrackIptablesRules=false
kubectl rollout restart -n kube-system ds/cilium

# 상태 확인
kubectl exec -it -n kube-system ds/cilium -- cilium status | grep ^Routing
# Routing: Network: Tunnel [vxlan] Host: BPF
ip -c addr show dev cilium_vxlan

VXLAN 적용 후 ip route에는 k8s-w0의 PodCIDR까지 모두 cilium_host로 잡히며, 실제 패킷은 eBPF가 가로채어 클러스터 내부 Endpoint/Service IP면 cilium_vxlan을 통해 UDP 8472 포트로 전송하고, 8.8.8.8 같은 외부 통신은 VXLAN을 타지 않습니다.
