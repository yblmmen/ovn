Node & Pod 네트워크 통신: Native vs VXLAN & GENEVE

서로 다른 네트워크 대역에 노드가 위치할 때 autoDirectNodeRoutes의 한계와 Static Routing, 그리고 이를 해결하는 VXLAN Overlay 모드의 동작 원리를 비교합니다.

Native Routing Mode와 타 대역 노드(k8s-w0) 통신 불가 원인

k8s-ctr과 k8s-w1은 같은 /24 대역에 있고, k8s-w0는 다른 네트워크 대역에 배치된 환경입니다. autoDirectNodeRoutes=true는 같은 L2에 있는 노드들을 대상으로만 PodCIDR 라우팅을 추가하므로, k8s-w1 경로는 추가되지만 k8s-w0 경로는 추가되지 않습니다.

  • Native 모드 장점: 추가 Overlay가 없어 MTU 손실이 없고 캡슐화/디캡슐화 과정이 없어 네트워크 지연과 서버 부하가 적습니다.
  • Native 모드 단점: 다른 네트워크 대역에 대해서는 BGP 에이전트나 네트워크팀의 라우팅 설정이 필요합니다.
bash
# Static Routing 수동 추가 시 통신은 가능하나, 노드/서비스 추가마다 수정이 필요해 비현실적
# k8s-ctr
ip route 172.20.0.0/16 via 192.168.10.200 dev eth1 proto static
# router
ip route add 172.20.2.0/24 via 192.168.20.100 dev eth2 proto static
ip route add 172.20.0.0/24 via 192.168.10.100 dev eth1 proto static

VXLAN Overlay Network Mode 구성 및 패킷 검증

NAT는 Src IP 자체를 변경하고 OS에서 상태를 추적하지만, VXLAN Tunnel은 기존 헤더에 Node IP와 VXLAN 헤더를 캡슐화(추가)해 전송하고 목적지에서 디캡슐화합니다. PodCIDR 라우팅을 고려할 필요가 없습니다.

bash
# 커널 모듈 확인 및 vxlan 로드
grep -E 'CONFIG_VXLAN=y|CONFIG_VXLAN=m|CONFIG_GENEVE=y|CONFIG_GENEVE=m|CONFIG_FIB_RULES=y' /boot/config-$(uname -r)
modprobe vxlan
for i in w1 w0 ; do
  sshpass -p 'vagrant' ssh vagrant@k8s-$i sudo modprobe vxlan
done

# Tunnel(VXLAN) 모드로 업그레이드 (변경 시 약 5개 ping 순단 발생)
helm upgrade cilium cilium/cilium --namespace kube-system --version 1.18.0 --reuse-values \
  --set routingMode=tunnel --set tunnelProtocol=vxlan \
  --set autoDirectNodeRoutes=false --set installNoConntrackIptablesRules=false
kubectl rollout restart -n kube-system ds/cilium

kubectl exec -it -n kube-system ds/cilium -- cilium status | grep ^Routing
# Routing: Network: Tunnel [vxlan] Host: BPF
cilium features status | grep cilium_feature_datapath_network
ip -c addr show dev cilium_vxlan

VXLAN 적용 후 ip route에는 k8s-w0의 PodCIDR까지 모두 cilium_host로 잡히지만, 실제 패킷은 eBPF가 가로채어 클러스터 내부 Endpoint/Service IP면 cilium_vxlan을 통해 UDP 8472 포트로 전송합니다. 반면 8.8.8.8 같은 외부 통신은 cilium_vxlan을 사용하지 않습니다.

실무 회고: 핀테크 환경처럼 지연 민감도가 높은 서비스에서는 Native 모드가 이상적이지만 커널 업그레이드와 네트워크팀 협업이 필요합니다. 현재 VXLAN 모드로 운영 중이나 최적화 튜닝을 통해 인프라 레벨의 지연을 줄여나가는 것이 목표입니다.

GENEVE Tunnel 모드 확인 (hyeonjae1122 추가 실습)

VXLAN(UDP 8472) 대신 GENEVE(UDP 6081) 프로토콜을 사용할 수도 있습니다. 모든 노드에서 modprobe geneve로 커널 모듈을 로드한 뒤 tunnelProtocol=geneve로 업그레이드하면 cilium_geneve(MTU 1500) 인터페이스가 생성되고, cilium_host를 경유하는 라우팅 테이블에 mtu 1450이 적용됩니다.

bash
# 모든 노드에 geneve 커널 모듈 로드
modprobe geneve

# GENEVE 터널 모드로 전환
helm upgrade cilium cilium/cilium --namespace kube-system --version 1.18.0 --reuse-values \
  --set routingMode=tunnel --set tunnelProtocol=geneve \
  --set autoDirectNodeRoutes=false --set installNoConntrackIptablesRules=false
kubectl rollout restart -n kube-system ds/cilium

# 확인
cilium features status | grep datapath_network
# mode=overlay-geneve
ip -c addr show dev cilium_geneve

# 라우터에서 UDP 6081 패킷 캡처 및 termshark 디코딩
tcpdump -i any udp port 6081 -w /tmp/geneve.pcap
termshark -r /tmp/geneve.pcap -d udp.port==6081,geneve
