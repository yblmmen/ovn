Cilium 개요 & 아키텍처 (Sidecarless)

전통적인 Sidecar 모델과 Cilium의 Sidecarless(eBPF + 노드당 1개 Envoy) 모델을 비교하고, Agent·Debug CLI·Operator·CNI Plugin·Hubble·Data Store 구성 요소를 정리합니다.

Sidecar vs Sidecarless (Cilium의 접근 방식)

구분전통적인 Sidecar 모델Cilium Sidecarless 모델
아키텍처모든 애플리케이션 파드마다 Envoy 사이드카 컨테이너 배포L3/L4는 커널 eBPF로 직접 처리, L7만 노드당 단일 Envoy 프록시로 리다이렉션
리소스 사용량모든 파드에 프록시 컨테이너가 추가되어 CPU/메모리 소비 급증프록시 수를 노드 수만큼으로 대폭 절감
지연 시간 & 기동모든 요청마다 추가 네트워크 홉 발생 및 사이드카 기동 대기L3/L4 트래픽에 추가 홉이 없어 낮은 지연과 빠른 기동

Cilium 핵심 구성 요소

  • Cilium Agent (DaemonSet): 각 노드에서 실행되며 K8s 이벤트/API를 수신해 네트워킹·보안 요구사항을 파악하고 eBPF 프로그램을 관리·로딩합니다.
  • Cilium Debug CLI (cilium-dbg): Agent 파드 내부에 설치되어 로컬 Agent REST API와 통신하며 eBPF 맵과 상태를 검사합니다(설치/관리용 cilium CLI와 구분).
  • Cilium Operator: 클러스터 전반에서 논리적으로 한 번만 처리할 작업(IPAM, kvstore 하트비트 등)을 관리합니다. 패킷 포워딩 Critical Path에는 없으나, 장애 시 IPAM 지연이 발생할 수 있습니다.
  • CNI Plugin (cilium-cni): 파드 스케줄링/종료 시 kubelet에 의해 호출되어 데이터패스를 설정합니다.
  • Hubble (Server / Relay / CLI / UI): 각 노드 Agent에 내장된 Hubble Server가 gRPC로 Flow를 제공하고, Relay가 클러스터 전체 데이터를 집계합니다.
  • eBPF & Data Store: 커널 Verifier와 JIT 컴파일러로 안전하고 빠르게 실행되며, 상태 전파는 기본 Kubernetes CRD(또는 대규모 최적화용 etcd kvstore)를 사용합니다.
