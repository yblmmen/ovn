테스트 환경 구성과 Cilium 개념 정리

Vagrant + VirtualBox 기반 Kubernetes 1.33 3노드 실습 환경 구축과 iptables의 한계, eBPF 커널 Hook 및 Native Routing 트래픽 검증 과정을 정리합니다.

학습 배경

가시다님이 주관하시는 Cilium 스터디를 진행하며 각 주제별로 이해한 내용을 정리한 글입니다. 첫 단계는 실습 환경 구성과 Cilium에 대한 기본 개념 및 설치입니다.

  • 아직까지는 부담스럽지 않은 시작 단계이지만, 뒤로 갈수록 점점 깊은 커널·네트워크 개념들이 등장합니다.
  • 트래픽 흐름에 대해서는 잘 모르는 분야여서 많이 찾아보았고, 지금까지 커널을 깊게 생각해본 적이 없어 "트래픽은 알아서 흐르겠지"라고만 생각했던 부분을 직접 확인해 보았습니다.

실습 환경 구성 (Vagrant + VirtualBox)

실습 환경은 Vagrant + VirtualBox로 구성합니다. 개인적으로 K8s 테스트를 할 때는 kind를 많이 이용했는데, kind에서는 일부 제약이 있어 이번에는 Vagrant로 진행합니다.

  • Vagrant: 가상환경을 만들고 쉽게 생성·관리하는 도구
  • VirtualBox: 가상환경을 만들어주는 하이퍼바이저
bash
## virtualbox Install
brew install --cask virtualbox
vBoxManage -v
# 7.1.10r169112

## vagrant Install
brew install --cask vagrant
vagrant --version
# Vagrant 2.4.7

Vagrant는 어떤 구성요소로 가상환경을 만들지 Vagrantfile이 필요하며, vagrant init을 하면 기본 포맷이 만들어집니다. OS 이미지는 HashiCorp(Ubuntu 또는 Rocky Linux 9 등)에서 제공합니다.

ruby
vagrant init hashicorp/bionic64

# ---Vagrantfile---
Vagrant.configure("2") do |config|
  config.vm.box = "hashicorp/bionic64"
end

스터디에서는 마스터 노드 1대(k8s-ctr)와 워커 노드 2대(k8s-w1, k8s-w2) 총 3대로 Kubernetes 1.33 클러스터를 구성했습니다. 노드 이미지는 bento/ubuntu-24.04를 사용했습니다.

ruby
# Variables
K8SV = '1.33.2-1.1'        # Kubernetes Version : apt list -a kubelet , ex) 1.32.5-1.1
CONTAINERDV = '1.7.27-1'   # Containerd Version : apt list -a containerd.io , ex) 1.6.33-1
N = 2                      # max number of worker nodes

# Base Image
BOX_IMAGE = "bento/ubuntu-24.04"
BOX_VERSION = "202502.21.0"
# BOX_IMAGE = "rockylinux/9"
# BOX_VERSION = "6.0.0"

Vagrant.configure("2") do |config|
  #-ControlPlane Node
  config.vm.define "k8s-ctr" do |subconfig|
    subconfig.vm.box = BOX_IMAGE
    subconfig.vm.box_version = BOX_VERSION
    subconfig.vm.provider "virtualbox" do |vb|
      vb.customize ["modifyvm", :id, "--groups", "/Cilium-Lab"]
      vb.customize ["modifyvm", :id, "--nicpromisc2", "allow-all"]
      vb.name = "k8s-ctr"
      vb.cpus = 2
      vb.memory = 2048
      vb.linked_clone = true
    end
    subconfig.vm.host_name = "k8s-ctr"
    subconfig.vm.network "private_network", ip: "192.168.10.100"
    subconfig.vm.network "forwarded_port", guest: 22, host: 60000, auto_correct: true, id: "ssh"
    subconfig.vm.synced_folder "./", "/vagrant", disabled: true
    subconfig.vm.provision "shell", path: "https://raw.githubusercontent.com/gasida/vagrant-lab/refs/heads/main/cilium-study/1w/init_cfg.sh", args: [ K8SV, CONTAINERDV ]
    subconfig.vm.provision "shell", path: "https://raw.githubusercontent.com/gasida/vagrant-lab/refs/heads/main/cilium-study/1w/k8s-ctr.sh", args: [ N ]
  end

  #-Worker Nodes Subnet1
  (1..N).each do |i|
    config.vm.define "k8s-w#{i}" do |subconfig|
      subconfig.vm.box = BOX_IMAGE
      subconfig.vm.box_version = BOX_VERSION
      subconfig.vm.provider "virtualbox" do |vb|
        vb.customize ["modifyvm", :id, "--groups", "/Cilium-Lab"]
        vb.customize ["modifyvm", :id, "--nicpromisc2", "allow-all"]
        vb.name = "k8s-w#{i}"
        vb.cpus = 2
        vb.memory = 1536
        vb.linked_clone = true
      end
      subconfig.vm.host_name = "k8s-w#{i}"
      subconfig.vm.network "private_network", ip: "192.168.10.10#{i}"
      subconfig.vm.network "forwarded_port", guest: 22, host: "6000#{i}", auto_correct: true, id: "ssh"
      subconfig.vm.synced_folder "./", "/vagrant", disabled: true
      subconfig.vm.provision "shell", path: "https://raw.githubusercontent.com/gasida/vagrant-lab/refs/heads/main/cilium-study/1w/init_cfg.sh", args: [ K8SV, CONTAINERDV ]
      subconfig.vm.provision "shell", path: "https://raw.githubusercontent.com/gasida/vagrant-lab/refs/heads/main/cilium-study/1w/k8s-w.sh"
    end
  end
end

Control Plane 초기화 (kubeadm init)

k8s-ctr.sh의 TASK 1에서 kubeadm init이 실행되면 /etc/kubernetes/pki에 인증서·키가 생성되고, /etc/kubernetes/manifest에 etcd, kube-apiserver, controller-manager, scheduler YAML이 생성되어 kubelet이 containerd를 통해 Static Pod로 기동합니다.

bash
echo "[TASK 1] Initial Kubernetes"
kubeadm init --token 123456.1234567890123456 --token-ttl 0 \
  --pod-network-cidr=10.244.0.0/16 --service-cidr=10.96.0.0/16 \
  --apiserver-advertise-address=192.168.10.100 \
  --cri-socket=unix:///run/containerd/containerd.sock >/dev/null 2>&1

일반적으로는 kubeadm-init-config.yaml을 작성해 초기화하고 kubeadm token list로 토큰을 확인합니다.

yaml
apiVersion: kubeadm.k8s.io/v1beta3
kind: InitConfiguration
localAPIEndpoint:
  advertiseAddress: 192.168.10.100
  bindPort: 6443
nodeRegistration:
  criSocket: unix:///run/containerd/containerd.sock
---
apiVersion: kubeadm.k8s.io/v1beta3
kind: ClusterConfiguration
networking:
  podSubnet: 10.244.0.0/16
  serviceSubnet: 10.96.0.0/16

Worker Node 조인 및 Node IP 설정

Worker 노드는 Control Plane의 토큰으로 조인합니다. 운영 환경이나 보안을 고려한다면 caCertHashes를 넣어 중간자 공격을 방지해야 합니다. 또한 노드 간 원활한 통신을 위해 eth1(192.168.10.x) IP를 kubelet --node-ip에 반영합니다.

bash
echo "[TASK 1] K8S Controlplane Join"
kubeadm join --token 123456.1234567890123456 --discovery-token-unsafe-skip-ca-verification 192.168.10.100:6443 >/dev/null 2>&1
yaml
apiVersion: kubeadm.k8s.io/v1beta3
kind: JoinConfiguration
discovery:
  bootstrapToken:
    apiServerEndpoint: "192.168.10.100:6443"
    token: "123456.1234567890123456"
    caCertHashes:
      - "sha256:9b2453ae661f2a119628edbc3921672b671e0533c7cea627d6e2b084da2260cb"
nodeRegistration:
  kubeletExtraArgs:
    node-ip: "192.168.10.102"
bash
NODEIP=$(ip -4 addr show eth1 | grep -oP '(?<=inet\s)\d+(\.\d+){3}')
sed -i "s/^\(KUBELET_KUBEADM_ARGS=\"\)/\1--node-ip=\${NODEIP} /" /var/lib/kubelet/kubeadm-flags.env
systemctl daemon-reexec && systemctl restart kubelet

여기까지만 진행하면 CNI가 아직 배포되지 않아 각 노드는 NotReady 상태입니다.

Cilium 개념 및 iptables와의 차이

Cilium은 eBPF 기술을 적용해 커널에 프로그램을 실행함으로써 유연성, 확장성, 보안성을 높이고자 하는 CNI입니다. 기존 iptables는 다음과 같은 3가지 한계가 있었습니다.

  1. 단일 트랜잭션 Rule 업데이트: Rule을 부분 추가/제거하는 것이 아니라 전체를 Save → Apply하는 방식(AWS WAF IPRuleSet과 유사)이라 엔드포인트가 자주 바뀌는 쿠버네티스 대규모 환경에서 시스템 자원 병목이 됩니다.
  2. L3/L4 IP·Port 기반의 한계: L7 애플리케이션 계층을 이해하고 트래픽을 제어하는 데 제약이 있습니다.
  3. 순차적 체인 매칭 구조: 상단 Rule부터 순차 비교하므로 Rule이 많아질수록 성능이 저하되고 트러블슈팅이 어렵습니다.

기존 CNI는 전통적인 리눅스 네트워크 스택을 건너뛰거나 변경하기 어려웠지만, Cilium은 tcx 같은 Hook에 접근해 패킷을 필터링하거나 XDP 같은 특수 모드에서 인터페이스 간 네트워크 제어도 수행합니다.

Cilium 설치 (Helm · Native Routing)

bash
helm repo add cilium https://helm.cilium.io/

helm install cilium cilium/cilium --version 1.17.5 --namespace kube-system \
  --set k8sServiceHost=192.168.10.100 --set k8sServicePort=6443 \
  --set ipam.mode="cluster-pool" \
  --set kubeProxyReplacement=true \
  --set ipam.operator.clusterPoolIPv4PodCIDRList={"172.20.0.0/16"} \
  --set ipv4NativeRoutingCIDR=172.20.0.0/16 \
  --set autoDirectNodeRoutes=true \
  --set routingMode=native \
  --set endpointRoutes.enabled=true \
  --set installNoConntrackIptablesRules=true \
  --set bpf.masquerade=true \
  --set ipv6.enabled=false
yaml
# helm get values cilium 결과
autoDirectNodeRoutes: true
bpf:
  masquerade: true
debug:
  enabled: true
endpointRoutes:
  enabled: true
installNoConntrackIptablesRules: true
ipam:
  mode: cluster-pool
  operator:
    clusterPoolIPv4PodCIDRList:
      - 172.20.0.0/16
ipv4NativeRoutingCIDR: 172.20.0.0/16
ipv6:
  enabled: false
k8sServiceHost: 192.168.10.100
k8sServicePort: 6443
kubeProxyReplacement: true
routingMode: native

Pod를 생성하면 clusterPoolIPv4PodCIDRList에 정의한 172.20.0.0/16 대역으로 Pod IP가 할당됩니다.

Cilium 트래픽 확인 (lxc 인터페이스 & cilium_lxc 맵)

routingMode: native + autoDirectNodeRoutes=true로 설치했으므로 같은 Pod IP 대역(172.20.0.0/16)에 대해서는 별도 NAT 없이 바로 Pod 인터페이스로 라우팅됩니다. Node-1의 nginx1에서 Node-2의 nginx-2로 curl 요청을 보내면 노드 호스트에서는 트래픽이 보이지 않고 nginx-2에서 nginx-1의 Pod IP가 그대로 확인됩니다.

반면 Pod eth0와 매핑된 Cilium lxc 인터페이스에서 tcpdump를 실행하면 트래픽이 정확히 관측됩니다.

bash
kubectl exec -it -n kube-system ds/cilium -- cilium endpoint list
# ENDPOINT 2439 | IDENTITY 40045 | 172.20.0.37 | ready

kubectl exec -it -n kube-system ds/cilium -- cilium endpoint get 2439 | grep lxc
# "interface-name": "lxca1b000fd95c4",

Cilium은 Pod를 할당할 때 Pod 정보(IP, 인터페이스)를 cilium_lxc 맵에 추가하고, 패킷의 목적지 IP를 확인한 뒤 L2 헤더를 추가해 목적지 Pod의 MAC 정보로 lxc 인터페이스에 바로 라우팅합니다.

핵심 요약
Cilium은 커널에 eBPF 프로그램을 직접 심어 Hook을 걸고, cilium_lxc 맵을 통해 커널 라우팅 테이블을 거치지 않고도 원하는 네트워크 동작을 수행합니다.
