Hubble을 통한 Cilium Traffic 가시성 확보

eBPF 커널 레이어에서 처리되는 패킷을 시각화하는 Hubble Relay/UI/CLI 설치와 CiliumNetworkPolicy(L3/L4 및 L7) 연동, Flowlog Export 구성을 정리합니다.

Hubble 개념과 설치

Hubble은 Cilium을 기반으로 eBPF를 활용해 트래픽에 대한 가시성을 확보할 수 있는 오픈소스입니다. eBPF를 사용하면 커널 레이어에서 처리되는 것이 많아 가시성 확보가 어려운데 이를 Hubble로 보완합니다.

기본적으로 Hubble API는 각 노드의 cilium-agent 범위에서 동작하지만, hubble-relay를 배포하면 클러스터 전체 범위로 확장된 API를 제공합니다. hubble-ui는 내부적으로 nginx를 사용해 NodePort(31234)로 접근할 수 있으며, 외부 통신에는 world identity가 표시됩니다.

bash
helm upgrade cilium cilium/cilium --namespace kube-system --reuse-values \
  --set hubble.enabled=true \
  --set hubble.relay.enabled=true \
  --set hubble.ui.enabled=true \
  --set hubble.ui.service.type=NodePort \
  --set hubble.ui.service.nodePort=31234 \
  --set hubble.export.static.enabled=true \
  --set hubble.export.static.filePath=/var/run/cilium/hubble/events.log \
  --set prometheus.enabled=true \
  --set operator.prometheus.enabled=true \
  --set hubble.metrics.enableOpenMetrics=true \
  --set hubble.metrics.enabled="{dns,drop,tcp,flow,port-distribution,icmp,httpV2:exemplars=true;labelsContext=source_ip\,source_namespace\,source_workload\,destination_ip\,destination_namespace\,destination_workload\,traffic_direction}"

Hubble CLI 및 Port-Forward

Hubble 클라이언트를 설치하고 cilium hubble port-forward로 로컬 4245 포트를 연결하면 hubble status 및 hubble observe를 바로 사용할 수 있습니다.

bash
HUBBLE_VERSION=$(curl -s https://raw.githubusercontent.com/cilium/hubble/master/stable.txt)
HUBBLE_ARCH=amd64
if [ "$(uname -m)" = "aarch64" ]; then HUBBLE_ARCH=arm64; fi
curl -L --fail --remote-name-all https://github.com/cilium/hubble/releases/download/$HUBBLE_VERSION/hubble-linux-${HUBBLE_ARCH}.tar.gz{,.sha256sum}
sudo tar xzvfC hubble-linux-${HUBBLE_ARCH}.tar.gz /usr/local/bin

cilium hubble port-forward&
hubble status
# Healthcheck (via localhost:4245): Ok
# Current/Max Flows: 9,801/12,285 (79.78%) Connected Nodes: 3/3

CiliumNetworkPolicy(CNP) 적용과 Hubble 관측

Star Wars 예제(deathstar, tiefighter, xwing)를 통해 정책 적용 전/후를 비교합니다. CNP의 가장 큰 장점은 Stateful 연결 정책을 지원한다는 점입니다. 기존 NetworkPolicy는 A→B를 허용하면 B→A도 열어줘야 했지만, CNP는 단방향 정책만 허용해도 응답 방향은 자동 허용됩니다.

yaml
apiVersion: "cilium.io/v2"
kind: CiliumNetworkPolicy
metadata:
  name: "rule1"
spec:
  description: "L3-L4 policy to restrict deathstar access to empire ships only"
  endpointSelector:
    matchLabels:
      org: empire
      class: deathstar
  ingress:
    - fromEndpoints:
        - matchLabels:
            org: empire
      toPorts:
        - ports:
            - port: "80"
              protocol: TCP
bash
# 차단된 트래픽만 필터링 조회
hubble observe -f --protocol tcp --pod deathstar --verdict DROPPED
hubble observe -f --from-identity {id}
hubble observe -f {pod_name}

L7 Rule 적용과 cilium-envoy 경로

CNP에 rules.http를 추가하면 Method와 Path 단위 제어가 가능하며, Hubble UI와 hubble observe --protocol http에서 HTTP 응답 코드와 latency까지 확인할 수 있습니다. L7 제어 시에는 Daemon 형태의 cilium-envoy를 거칩니다.

yaml
apiVersion: "cilium.io/v2"
kind: CiliumNetworkPolicy
metadata:
  name: "rule1"
spec:
  description: "L7 policy to restrict access to specific HTTP call"
  endpointSelector:
    matchLabels:
      org: empire
      class: deathstar
  ingress:
    - fromEndpoints:
        - matchLabels:
            org: empire
      toPorts:
        - ports:
            - port: "80"
              protocol: TCP
          rules:
            http:
              - method: "POST"
                path: "/v1/request-landing"

Hubble Flowlog Export (Static vs Dynamic)

콘솔 출력뿐만 아니라 로그 수집 시스템/SIEM 연동을 위해 파일로 저장할 수 있습니다. static은 ConfigMap 수정 후 rollout이 필요하고 1개만 지정 가능한 반면, dynamic은 별도 ConfigMap(cilium-flowlog-config)으로 재시작 없이 자동 반영되며 다수 경로/필터 지정이 가능합니다.

yaml
export:
  fileMaxSizeMb: 10
  fileMaxBackups: 5
  static:
    enabled: false
    filePath: /var/run/cilium/hubble/events.log
  dynamic:
    enabled: false
    config:
      configMapName: cilium-flowlog-config
      createConfigMap: true
      content:
        - name: all
          fieldMask: []
          includeFilters: []
          excludeFilters: []
          filePath: "/var/run/cilium/hubble/events.log"
